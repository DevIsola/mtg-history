# Phase 4 — Accessibility and production performance baselines

The objective is to **measure first, remediate, then introduce justified budgets**.
A successful smoke test is not a WCAG certification, and a localhost timing is not
an actual visitor's Core Web Vitals score.

## Requirements and local setup

The existing browser suite uses Playwright. Add the axe integration once and
commit the resulting manifest and lockfile in the same pull request:

```bash
pnpm add -D -E @axe-core/playwright
pnpm install --frozen-lockfile
pnpm exec playwright install chromium
pnpm run verify
pnpm exec playwright test
pnpm exec playwright test --config playwright.performance.config.mjs
```

The final command requires a production `dist/`, generated by `pnpm run verify`
or `pnpm run build`. It serves Astro through `astro preview` on port 4322, not
`astro dev` on port 4321. Both suites run Chromium desktop and emulated mobile.

## Accessibility audit

`tests/browser/accessibility.spec.mjs` runs axe against the home, timeline,
characters, events, archive, discovery and Chapter 08 routes. It records WCAG
2.0/2.1 A and AA rules plus WCAG 2.2 AA rules. Every page produces an
`accessibility-baseline.json` file in its Playwright test output folder with:

- Rule ID, severity, remediation URL, affected selectors, and issue details.
- Incomplete rules that still require human review.
- Number of passed and scanned rules.

**By design, the initial scan does not fail for reported violations**. This
prevents a clean CI check from being misrepresented as a clean accessibility
scan. CI logs include the number of findings and uploads the full artifact.
Review serious and critical issues first, then moderate/minor ones. Retest with
keyboard-only navigation, VoiceOver on macOS/iOS, and reduced-motion/contrast
preferences. Automated scans do not evaluate all WCAG requirements.

Once the observed baseline has been remediated, the optional policy
`A11Y_ENFORCE=1 pnpm exec playwright test tests/browser/accessibility.spec.mjs`
will fail if any serious or critical axe issues remain. Consider making this
mandatory in CI only after explicit review of initial findings.

## Production performance audit

`playwright.performance.config.mjs` starts `astro preview` with a previously
built `dist/`. `tests/performance/baseline.spec.mjs` records, per route/device:

- HTML response and DOMContentLoaded timing.
- First Contentful Paint (FCP); observed Largest Contentful Paint (LCP).
- Cumulative Layout Shift (CLS) during the short measurement window.
- Same-origin transferred/decoded resource bytes and request counts.

A missing metric is recorded as `null`, never as an invented value. Resource
bytes reflect same-origin requests, excluding external Scryfall imagery and
other hosts, and can be zero when data is unavailable. Mobile emulation is not
a substitute for throttling representative mobile hardware and networks.
The early observer window may not include late shifts/images.

These are **local laboratory snapshots** suitable for comparing changes run
with similar hardware and settings. They are **not** real-user data, a
75th-percentile field CWV assessment, or a Lighthouse performance score.
There is deliberately no guessed numerical budget. Run at least three clean
measurements, compare typical values and variance, then set reviewed thresholds
on a follow-up PR. Performance and accessibility should be retested after
major content/image changes, and then tested on production hosting.

## CI and artifacts

`.github/workflows/browser-quality.yaml` performs three stages after a merge to main (called by Pages), or by manual dispatch:

1. Existing browser interaction and accessibility scans (Astro dev).
2. Generate the production build.
3. Record production performance snapshots (Astro preview).

The workflow uploads `test-results/` on both passing and failing runs. In GitHub,
open the Browser quality run and download **browser-quality-baselines**; the
per-test JSON files are the baseline evidence. When reviewing regressions,
retain the report from the previous merge and compare it to the new run.

Existing Site quality and Browser quality failures remain blocking. Never
silently disable a failing test to get a green status.
